# SPA Prototype v0.3

Single Packet Authorization. Хост закрыт для всего входящего трафика (все порты и протоколы, IPv4 и IPv6,
ping тоже). Клиент «стучит» зашифрованным UDP-обменом; если пароль верный, его IP попадает в whitelist
nftables. При любой ошибке сервер молчит.

## Установка и использование

```sh
go mod tidy
go build -o spa-server ./cmd/spa-server
go build -o spa-cli ./cmd/spa-cli                         # клиент: linux / windows / macOS
GOOS=windows GOARCH=amd64 go build -o spa-cli.exe ./cmd/spa-cli

sudo ./spa-server init           # один раз; лучше с консоли сервера, а не по SSH
```

`init` (на английском) работает в таком порядке:

1. показывает предупреждение (важное выделено красным) и список найденных файрволов; без ввода `yes` ничего не меняется;
2. **после согласия** спрашивает UDP-порт стука (1024-65535, без значения по умолчанию; проверяет диапазон и что порт
   не занят ни по UDP, ни по TCP) и срок хранения IP в минутах (Enter = бессрочно). Порт можно задать флагом `--port`;
3. при необходимости ставит nftables;
4. генерирует пароль (20 символов `a-zA-Z0-9`) и показывает его салатовым **один раз**;
5. сохраняет ключ, конфиг и ruleset, ставит бинарник и systemd-юниты;
6. останавливает и отключает ufw, firewalld, nftables.service, netfilter-persistent, iptables, docker и др., сбрасывает все правила;
7. применяет ruleset, **проверяет**, что цепочка input действительно в режиме drop, и запускает демон.

Всё готовится **до** блокировки. Текущая SSH-сессия **может** оборваться, а может и нет: так, не рвутся сессии, которые
приходят не как входящее соединение (исходящий туннель, SSM, веб-консоль гипервизора, serial). Рассчитывать на неё нельзя.

```sh
spa-cli --host SERVER --port PORT [--timeout 30s] [--password-stdin]   # клиент, порта по умолчанию нет
sudo spa-server status              # порт, активен ли файрвол (default-deny), демон, число клиентов
sudo spa-server list                # номер, IP, когда добавлен, сколько осталось
sudo spa-server delete <номер|ip>   # удалить; соединения этого IP обрываются
sudo spa-server save                # сохранить live-ruleset на диск (после ручных правок nft)
```

Номер клиента: 1, 2, 3... Повторный «стук» с того же IP сохраняет его номер, новый IP получает max+1
(номер удалённого клиента не переиспользуется, пока существует клиент с большим номером).

## Файлы на сервере (`/etc/spa`, каталог 0700)

| Файл | Назначение |
|------|------------|
| `key` (0600) | производный ключ (Argon2id от пароля). Сам пароль не хранится. Демон стартует с ним после перезагрузки |
| `config.json` (0600) | выбранный порт и срок хранения IP |
| `nftables.conf` (0600) | снимок ruleset, загружается при загрузке юнитом `spa-firewall.service` до сети |

Базы данных нет: whitelist это set `inet spa allowed` в nftables. Элемент хранит комментарий
`id=<номер> added=<время>` и, если задан срок, родной `timeout` nftables (истекает сам).
Снимок пишется после каждого изменения, раз в минуту (если есть срок) и при остановке демона.
Ручные правила, добавленные через `nft`, сохраняются командой `spa-server save`.

## Правила файрвола

Вход: политика `drop` для всего, кроме loopback, ответов на **наши** исходящие соединения
(`ct state established ct direction reply`, именно это обрывает любые входящие, включая SSH), UDP-порта стука,
DHCP-ответов (`udp sport 67 dport 68`) и адресов из whitelist (им открыто всё). Выход: разрешён всё,
кроме ICMP `destination-unreachable` (хост не выдаёт «порт закрыт»). IPv6: любой входящий заблокирован.

## Протокол v3 (без времени)

Время нигде не участвует: синхронизация часов не нужна, и подделать нечего. Защита от повторов это challenge-response:

```
client -> HELLO(token)                          сервер выбирает случайный challenge
client <- CHALLENGE(token, challenge, ваш IP)
client -> OPEN(token, challenge, ваш IP)        сервер проверяет challenge и IP источника, добавляет IP
client <- OK(token, challenge, открытый IP)
```

- Пакет всегда 66 байт: `nonce(12) | ChaCha20-Poly1305(frame) | tag(16)`; открытых заголовков нет.
  Все четыре сообщения одного размера: усиления нет.
- Ключ: `Argon2id(пароль)` -> HKDF -> **отдельные** ключи client->server и server->client:
  отражать запрос обратно как «OK» нельзя. OK содержит token и challenge этого обмена, поэтому клиент
  принимает только настоящий ответ на свой запрос.
- Challenge одноразовый, живёт 2 минуты и привязан к IP, с которого пришёл HELLO. Перехваченный OPEN с другого
  адреса отклоняется молча, а сам IP узнаётся сервером из пакета, клиенту знать свой внешний адрес за NAT не нужно.
- Клиент повторяет **тот же** пакет (0.4 с, 0.64 с, ... до 5 с) до ответа или до `--timeout`.
  Дубликат с того же IP не повторяет действие в файрволе, а только заново отправляет ответ (не более 20 раз).
  Дубликат с другого IP игнорируется.
- Если nftables не смог добавить IP, сервер не отвечает OK.

## Проверка условий безопасности

1. **Только пароль, без соли.** Argon2id требует параметр salt, передаётся публичная константа (не секрет).
2. **Сброс файрволов при установке.** Делает `init` (см. выше).
3. **Нельзя получить пароль / подделать пакет.** Подделка и повтор невозможны (AEAD, разные ключи направлений,
   одноразовый challenge с привязкой к IP). Пароль генерируется (~119 бит), поэтому офлайн-подбор по
   перехваченному пакету нереалистичен, несмотря на отсутствие соли.
4. **Ответ только на верный пакет.** Ответ шифруется и привязан к запросу; всё остальное молчание.

## Как читать nmap (частый вопрос)

Сканировать нужно с адреса, которого **нет** в `spa-server list`. Адрес из whitelist видит хост как обычный
открытый сервер, и это штатно:

| Результат nmap | Что значит |
|----------------|------------|
| `Host seems down` (без `-Pn`) | цель достигнута: ping/TCP-пробы не получили ничего |
| `Host is up, received reset` | на TCP-пробу (443/80) пришёл RST: порт «закрыт», но **достижим**. Сканирующий IP в whitelist, либо файрвол не активен |
| `-sU -p PORT` -> `open\|filtered no-response` | штатно: демон слушает порт и молчит. Так выглядят *все* UDP-порты закрытого хоста |

Результат «то up, то down» объясняется записью в whitelist, которая истекает (или вы стучали между сканами).
Проверка: `sudo spa-server status` и `sudo spa-server list` в момент скана. Если адреса сканера в списке нет, а
`status` пишет `active`, но RST всё равно приходит, смотрите на сервере исходящие RST
(`sudo tcpdump -ni any 'tcp[tcpflags] & tcp-rst != 0'`): если их нет, RST отправляет не ваш хост, а оборудование провайдера.

## Что стоит знать

- **Повтор перехваченного HELLO** (с верным паролем) получит от сервера CHALLENGE, зашифрованный
  ключом, которого у атакующего нет: использовать его нельзя. Но это единственный случай, когда сервер
  отвечает тому, кто пароля не знает. Сервер помнит token 2 минуты, после этого повтор снова получает ответ.
- **Потеря пароля:** повторный `spa-server init` создаёт новый (старый перестаёт работать, список клиентов очищается).
- **IPv6** полностью закрыт (в том числе из-за этого не работает NDP, и IPv6-связность хоста
  фактически отключена). Клиенты и whitelist: только IPv4.
- **Срок после перезагрузки** считается от последнего снимка (не более минуты расхождения плюс время простоя).
- **Docker/контейнеры** отключаются при установке.
- **Порт из диапазона исходящих соединений** (по умолчанию 32768-60999) работает, но в редких случаях может быть
  занят исходящим соединением при загрузке до старта демона. `init` предупреждает об этом.

## Что проверено

Автотесты (`go test ./...`): протокол, сервер (повторы, чужой IP, истёкший challenge, сбой файрвола, бюджет повторов),
клиент с потерями пакетов в обе стороны, генератор паролей, проверка порта (занятый UDP/TCP), нумерация клиентов,
предупреждение (цвета, нет номера порта), nft-слой на подставном раннере и на **настоящем nft**
(`SPA_NFT_TEST=1 unshare -n ./firewall.test`). Сквозной прогон в двух сетевых пространствах с реальными бинарниками:
ping/TCP закрыты, стук открывает, `list`/`delete` по номеру и по IP, `status`, обрыв уже установленного TCP-соединения,
отсутствие ICMP-ответов (в том числе на исключение DHCP), поведение nmap-проб до/после «стука».

**Не проверено в среде разработки:** оркестрация `init` через systemd (отключение сервисов, установка пакета
nftables, юниты, автозагрузка). Код есть, но выполнялся только режим `init --files-only`. Первый запуск на живой
машине делайте с консоли сервера.
